# Network Picasso — Roadmap Implementation Plan

## Overview

This plan covers seven feature tracks for the Network Picasso local-first IBM Cloud architecture workbench. Each track is scoped as an independent sub-task that can be implemented and reviewed one at a time. The tracks build on each other in the order listed — question-answer persistence (T2) must come before Ollama integration (T1) makes full use of its results, and project management (T6) should land before tests (T7) so the folder layout is stable.

**Design principles that must not change:**
- Local-first. No cloud API keys, no remote model required to run.
- Deterministic renderer. Draw.io XML is generated by code, not raw LLM output.
- Canonical JSON model (`architecture.schema.json`) is the single source of truth.
- No new Python runtime dependencies beyond the stdlib unless absolutely necessary (Ollama uses a plain HTTP call).
- Carbon UI design language throughout.

**Confirmed decisions:**
- LLM confidence threshold: ≥ 0.8 merges silently; < 0.8 goes to the staging table.
- Ollama base URL: strictly `http://localhost:11434` for the initial version (no remote support needed).
- Project root folder is configurable via `inputs/settings.json` (`projectsRoot` key). Defaults to `inputs/projects/` inside the repo. The setting is exposed in the Settings panel so the architect can point it at any folder on their machine (e.g. `~/Documents/NetworkPicasso/projects/`).

## T1 — Ollama / Local LLM Integration

**Status:** `[ ] pending`

### Intent
Wire a local Ollama instance into the intake and question pipeline so that AI can augment (not replace) the existing rule-based engine. The LLM performs two roles: (a) deep document review to extract components the heuristic keyword scanner misses, and (b) confidence-scored placement of ambiguous components into the correct `ibm_cloud` key so the architect can verify uncertain assignments. The rules engine continues to run regardless of mode — LLM output is additive.

### Model Selection
All Ollama models should be supported via a configurable selector. The recommended default is **phi4:latest** (Microsoft Research; tested against this codebase's extraction and gap-analysis tasks — 9/9 correct component placements, 0.9–1.0 confidence, strong structured JSON output). Granite3.2 and all other locally-installed models are available via the dropdown. The settings panel lists every model returned by Ollama's `/api/tags` endpoint at runtime. The active model is stored in the global `inputs/settings.json` and overridable per-project via a `settings` key in `architecture.json`.

### Expected Outcomes
- Settings panel in the UI exposes: Mode toggle (Rules only / Ollama assisted), Ollama base URL (default `http://localhost:11434`), model selector (populated dynamically from `/api/tags`), and a "Test connection" button.
- In Ollama-assisted mode, intake sends the raw document text to the LLM with a structured prompt requesting a JSON response containing extracted components with a `confidence` field (0.0–1.0) and a `suggested_key` field (the `ibm_cloud` key it should go into).
- High-confidence components (≥ 0.8) are merged silently into the architecture model.
- Low-confidence components (< 0.8) are surfaced in the new Component Verification staging table (see T2) before the design-gap questions run.
- After component confirmation, the LLM also runs a gap-analysis prompt and returns additional questions beyond the rule-based 11. These are tagged `source: "llm"` and appear in the Questions panel alongside rule-based questions tagged `source: "rules"`.
- Falling back gracefully: if Ollama is unreachable, the server logs a warning and falls back to rules-only mode. No UI crash.

### Todo List
1. Add `src/network_picasso/ollama.py` — a thin client wrapping Ollama's HTTP API (`/api/generate`, `/api/tags`). No third-party library; use `urllib.request`. Expose: `list_models(base_url)`, `extract_components(text, model, base_url) -> list[dict]`, `generate_questions(architecture, model, base_url) -> list[dict]`.
2. Define the extraction prompt template inside `ollama.py`. The prompt must request a JSON array of `{ name, suggested_key, purpose, confidence, notes }`. Include a system instruction explaining all valid `ibm_cloud` keys and what belongs in each.
3. Define the gap-analysis prompt template. The prompt receives the full architecture JSON and asks the LLM to identify design gaps beyond the rule-based checks, returning `{ area, question, guidance, source: "llm" }` objects.
4. Update `server.py`: add `GET /api/ollama/models` that proxies Ollama's `/api/tags` (at `http://localhost:11434`) and returns a list of model names. Add `GET /api/settings` and `POST /api/settings` to read/write `inputs/settings.json`. The settings schema includes: `mode` (rules/ollama), `ollamaModel` (string), `confidenceThreshold` (float, default 0.8), `projectsRoot` (string, default `inputs/projects`).
5. Update `run_intake()` in `server.py` to accept a `mode` and `ollama_settings` payload. In Ollama-assisted mode, call `ollama.extract_components()` on the concatenated text of all uploaded files, merge high-confidence results into facts before building the architecture, and return low-confidence results separately as `pendingComponents`.
6. Add `Question` type extension: add optional `source: "rules" | "llm"` field. Update `find_design_gaps()` in `questions.py` to tag all returned questions with `source: "rules"`. LLM-generated questions come back from `ollama.generate_questions()` already tagged.
7. Add Settings panel to the UI (the existing SideNavLink for Settings has no content yet). Use Carbon `Toggle` for mode, `TextInput` for base URL, `Dropdown` for model (populated from `/api/ollama/models`), and `Button` for test connection. Store settings in React state and `POST /api/settings` on save.
8. Thread `mode` and `ollamaSettings` from Settings state into `uploadAndRunIntake()` and `runIntake()` calls so the server receives the current settings on every intake run.
9. Update `Question` type in `App.tsx` to include optional `source` field. Render a small tag ("AI" vs "Rules") next to each question's area tag in the Questions panel.

## T2 — Question-Answer Persistence and Component Back-Fill

**Status:** `[ ] pending`

### Intent
Today, architect answers live only in React state (`answeredQuestions`) and are lost on page refresh. This task writes answers permanently into the architecture JSON through a new API endpoint, and — crucially — attempts to parse the answer text back into the relevant `ibm_cloud` key so the diagram improves automatically when a question is answered. The `questions.answered` array becomes a structured audit trail with `{ area, question, answer, source, timestamp }` objects, not just strings.

### Component Verification Staging Table
A new UI step sits between intake completion and the Questions panel. After any intake run (upload or local path), if there are `pendingComponents` (low-confidence LLM extractions, or in rules-only mode this step is skipped unless the LLM is enabled), the UI shows a staging table with columns: Name · Suggested placement (ibm_cloud key) · Confidence · Notes · Action (Confirm / Reassign / Discard). Confirmed components are written into the model immediately. Remaining ambiguities that survive this step are converted into Questions panel items tagged "Component verification".

### Expected Outcomes
- `POST /api/answer` endpoint accepts `{ architecturePath, area, question, answer, source }` and writes to the on-disk architecture JSON atomically.
- The answered entry is written as `{ area, question, answer, source, timestamp }` into `architecture.questions.answered`.
- The answer text is run through a lightweight back-fill function (reuses `intake.py` patterns) to extract component hints and append them to the relevant `ibm_cloud` key with `source: "architect-answer"`.
- If Ollama is enabled, the back-fill step uses the LLM instead of keyword matching for higher accuracy.
- The `questions.open` array on disk is updated to remove the answered question.
- The UI calls `POST /api/answer` inside the existing `saveAnswer()` and `acceptCoaching()` functions.
- `architecture.questions.answered` is loaded on the `/api/example` and `/api/intake` responses so previously answered questions survive a page refresh.
- `mergeQuestions()` is updated to exclude questions whose key appears in the loaded `answered` list.
- `POST /api/confirm-components` accepts `{ architecturePath, confirmed: [{name, key, purpose, notes}], discarded: [name] }` and writes confirmed components into the architecture JSON.
- The staging table UI component is added between the upload panel and the Questions panel; it only renders when `pendingComponents.length > 0`.

### Todo List
1. Update `schemas/architecture.schema.json` — change `questions.answered` from `array of string` to `array of { area, question, answer, source, timestamp }`.
2. Add `POST /api/answer` to `server.py`. Load the architecture JSON, append to `answered`, remove from `open`, run `backfill_answer_into_model()`, write back atomically using a temp file + rename.
3. Write `backfill_answer_into_model(architecture, area, answer)` in `intake.py`. For each `ibm_cloud` key that corresponds to the answered area, run the existing keyword-detection logic against the answer text and append any detected components with `source: "architect-answer"`. Re-run `dedupe_components()` after.
4. Add `POST /api/confirm-components` to `server.py`. Accepts confirmed and discarded lists. Writes confirmed items into the correct `ibm_cloud` keys.
5. Update `run_intake()` in `server.py` to load existing `answered` entries from a pre-existing architecture file at `outputPath` (if it exists) and merge them into the new model so answers survive re-intake.
6. Update `/api/example` and `/api/intake` responses to include `answeredQuestions` as a structured list so the UI can pre-populate state on load.
7. Update `App.tsx` — `saveAnswer()` and `acceptCoaching()` call `POST /api/answer` after updating local state. Add `AnsweredQuestion` type. Load answered questions from intake/example response and seed `answeredQuestions` state.
8. Add `ComponentVerification` UI component in `App.tsx` (or a new `ui/src/ComponentVerification.tsx`). Render a Carbon `DataTable` with Name, Suggested Key, Confidence, Notes columns and Confirm/Reassign/Discard inline actions. Call `POST /api/confirm-components` on submit.
9. Update `mergeQuestions()` to accept an `answered` list and filter already-answered keys.

### Relevant Context
- `src/network_picasso/server.py` — `run_intake()`, `handle_questions()`, `read_json_file()`
- `src/network_picasso/intake.py` — `add_detected_facts()`, `dedupe_components()`, `CATEGORY_ALIASES`

## T3 — IBM Cloud Solutioning Workbook Extraction

**Status:** `[ ] pending`

### Intent
The IBM Cloud Solutioning pricing workbook is the most common source file in customer engagements. It has a well-known sheet structure (Summary, Detailed Estimate, etc.) with specific column names ("Part Number", "Part Description", "Quantity", "Monthly Recurring Charge", "Category"). The current heuristic XLSX parser treats all sheets identically via keyword scan. This task adds an explicit sheet/column recognition layer that fires first when a Solutioning workbook is detected, producing far more accurate component extraction.

### Expected Outcomes
- A new `read_solutioning_xlsx()` function in `intake.py` detects a Solutioning workbook by looking for known sheet names ("Summary", "Detailed Estimate") and/or column headers ("Part Number", "Part Description").
- When detected, it maps Solutioning-specific columns to component fields: Part Description → `name`, Category → `type` (mapped through `CATEGORY_ALIASES`), Notes/Region columns → `notes`/`region`.
- Falls back to the generic `read_xlsx()` path if detection fails.
- A `source_format: "ibm-solutioning"` field is added to the source entry in `architecture.sources` so the UI and renderer can note the source type.
- Sample Solutioning workbook structure is documented in a new `docs/solutioning-workbook-format.md` so future contributors know what columns to expect.
- Existing `read_xlsx()` path is unchanged for non-Solutioning files.

### Todo List
1. Research and document the IBM Cloud Solutioning workbook sheet/column structure in `docs/solutioning-workbook-format.md`. Include known sheet names, key columns, and category values used in real exports.
2. Write `is_solutioning_workbook(archive: ZipFile) -> bool` in `intake.py`. Returns True if the workbook contains a sheet named "Detailed Estimate" or "Summary" with a "Part Number" column in the first row.
3. Write `read_solutioning_xlsx(path: Path) -> Iterable[dict[str, str]]` in `intake.py`. Parse the "Detailed Estimate" sheet (falling back to "Summary") using the known column names. Yield normalized rows with consistent keys: `component`, `category`, `region`, `notes`, `part_number`, `quantity`.
4. Update `read_input_rows()` to call `is_solutioning_workbook()` before `read_xlsx()` for `.xlsx` files and route accordingly.
5. Add `part_number` and `quantity` to the component schema as optional fields in `schemas/architecture.schema.json`.
6. Update the source entry in `build_architecture_from_inputs()` to include `source_format` when a Solutioning workbook is detected.
7. Add a small representative sample Solutioning-style CSV or XLSX fixture under `examples/sample-inputs/` for use in tests (T7).

### Relevant Context
- `src/network_picasso/intake.py` — `read_xlsx()`, `read_input_rows()`, `parse_sheet_rows()`, `parse_workbook_sheets()`, `CATEGORY_ALIASES`
- `schemas/architecture.schema.json` — component object `additionalProperties: true` means new fields can be added without a breaking change

## T4 — Draw.io Renderer Improvements

**Status:** `[ ] pending`

### Intent
The current renderer produces a flat region box with generic ingress/compute/data/security/observability blobs. This task adds real IBM Cloud VPC topology: availability zones as swim lanes within a VPC, subnet tiers (public/private/management/data) within each zone, and proper visual conventions for PowerVS, VSI, ROKS, Bare Metal on VPC, VPE gateways, and Transit Gateway. The result should look like a professional IBM Cloud deployment architecture diagram.

### Expected Outcomes
- VPC boxes contain three AZ columns (zone-1, zone-2, zone-3) laid out side by side.
- Each AZ column contains up to four subnet tier rows: Public, Private, Management, Data — rendered as horizontally-striped bands with IBM color conventions.
- Compute components are placed inside the correct subnet tier: ROKS/VSI in Private, Load Balancers in Public, Bastion/Jump in Management, Databases in Data.
- PowerVS workspace rendered as a distinct boundary box outside the VPC with a bridge arrow representing the PowerVS cloud connection or Transit Gateway link.
- Transit Gateway rendered as a central hub box between VPCs/regions with spokes to each connected VPC.
- VPE gateways rendered as small gateway icons inside the private subnet tier with dotted lines to the IBM Cloud services they front.
- `DrawioBuilder` gains new helpers: `zone_column()`, `subnet_band()`, `powervs_workspace()`, `transit_gateway_hub()`, `vpe_gateway()`.
- All three diagram types (context, logical, deployment) are updated; context remains high-level, deployment gets the full AZ/subnet layout.

### Todo List
1. Define a layout constants block at the top of `drawio.py`: AZ column width, subnet band heights, color palette for each tier (matching IBM Cloud diagram conventions).
2. Add `zone_column(label, x, y, width, height)` to `DrawioBuilder` — renders a zone boundary with a label at the top.
3. Add `subnet_band(label, x, y, width, height, tier)` to `DrawioBuilder` — tier drives fill color: Public=#dae8fc, Private=#d5e8d4, Management=#fff2cc, Data=#e1d5e7.
4. Refactor `render_drawio()` — extract `_render_deployment()`, `_render_logical()`, `_render_context()` as separate functions. Deployment calls the new zone/subnet layout; context stays as the current simple layout; logical is an intermediate.
5. In `_render_deployment()`, place extracted compute components into subnet tiers based on their `type` and `purpose` text: ingress → Public tier, compute → Private tier, security/management → Management tier, data → Data tier.
6. Add `powervs_workspace()` helper. Renders a distinct box to the right of the IBM Cloud Account boundary with a "PowerVS" label and a link back to the Transit Gateway or VPC.
7. Add `transit_gateway_hub()` helper. Renders a central hub node and spoke edges to each connected VPC node ID.
8. Add `vpe_gateway()` helper. Renders a small gateway box inside a private subnet band with a dotted edge to the backing service (e.g. Cloud Object Storage).
9. Update the IBM Cloud color palette in `drawio.py` to match the official IBM Cloud diagram stencil colors.
10. Update `examples/sample/architecture.json` to include `zone` and `subnet_tier` hints on a few components so the new layout has data to work with.

### Relevant Context

- `src/network_picasso/server.py` — `handle_generate_drawio()` — passes `architecture` and `diagram_type`

## T6 — Project / Workspace Management

**Status:** `[ ] pending`

### Intent
Replace the single `inputs/uploads/current/` workspace with a hierarchical project system. Folder structure supports customer → project nesting so one instance of Network Picasso can manage multiple engagements. The UI sidebar gains a real project browser. The existing "current" workspace remains operational as the default until the user creates a named project.

### Folder Structure
The project root is configurable. The default is `inputs/projects/` inside the repo, but the architect can point `projectsRoot` in `inputs/settings.json` at any absolute path on their machine (e.g. `~/Documents/NetworkPicasso/projects/`). This is exposed as a text field in the Settings panel.

```
<projectsRoot>/
  <customer-slug>/
    <project-slug>/
      uploads/          ← source files for this project
      architecture.json ← canonical model
  <customer-slug>/
    architecture.json   ← single-project customer (no sub-project folder)
```

A project is identified by its path relative to `projectsRoot`. The server resolves `projectsRoot` from `inputs/settings.json` on every request (no restart needed when it changes). The folder tree is the source of truth — no separate index file.

### Expected Outcomes
- `GET /api/projects` scans `inputs/projects/` and returns a tree of `{ customer, project, path, hasArchitecture }` objects.
- `POST /api/projects` creates a new customer folder, optionally with a project sub-folder. Sanitizes slugs.
- `DELETE /api/projects/:path` removes a project folder (with confirmation guard in the UI).
- `GET /api/project/:path/export` returns the `architecture.json` as a file download.
- `POST /api/project/:path/import` accepts an `architecture.json` upload and writes it into the project folder.
- The sidebar replaces the static SideNavLinks with a live project tree loaded from `/api/projects`. Clicking a project sets the active `architecturePath` in the UI.
- The "Upload source material" panel's project name field creates a new project when the intake is run (via a "New project" vs "Existing project" toggle).
- The `inputs/uploads/current/` legacy path continues to work; it appears in the project tree as "Unsaved workspace".

### Todo List
1. Add `src/network_picasso/projects.py` — functions: `list_projects(root)`, `create_project(root, customer, project)`, `project_path(root, customer, project)`, `safe_slug(name)`. The `root` argument is always resolved from `load_settings()["projectsRoot"]` in the caller, never hard-coded.
2. Add `GET /api/projects`, `POST /api/projects`, `GET /api/project-export`, `POST /api/project-import` to `server.py`. Route project-specific intake paths through `projects.py`.
3. Update `handle_upload_intake()` and `handle_intake()` in `server.py` to accept optional `customer` and `project` fields in the payload and resolve the upload/architecture path via `projects.py` instead of hard-coded constants.
4. Add project state to `App.tsx`: `activeProject`, `projectTree`. Load project tree on mount from `/api/projects`.
5. Replace the static `SideNavItems` in the sidebar with a dynamic project tree. Use Carbon `SideNavMenu` for customer nodes and `SideNavMenuItem` for project nodes.
6. Add "New project" flow: a Carbon `Modal` with Customer name + Project name inputs. On submit, `POST /api/projects` and refresh the project tree.
7. Update the upload panel to use the active project path (or create a new project during upload via the modal). Update the Settings panel to include a `projectsRoot` text input (and a folder-browse hint since browsers cannot browse local directories directly). On save, `POST /api/settings` with the new root and refresh the project tree.
8. Add export button to the Architecture Model panel: calls `GET /api/project-export` and triggers a browser file download.
9. Add import button: opens a file picker for `.json` files and `POST /api/project-import`.
10. Update `.gitignore` to ensure `inputs/projects/` is ignored (same as `inputs/uploads/`).

### Relevant Context

## Implementation Order

The sub-tasks should be implemented in this sequence:

```
T2 (answer persistence) → T3 (Solutioning XLSX) → T1 (Ollama) → T4 (renderer) → T5 (XML endpoint) → T6 (projects) → T7 (tests)
```

**Rationale:**
- T2 first because it fixes the most important data-loss issue (answers disappearing on refresh) and its `backfill_answer_into_model()` function is reused by T1's LLM answer handling.
- T3 before T1 so the Solutioning-format detection exists before the LLM extraction prompt references column names from real workbooks.
- T1 after T2 and T3 because it builds on both the answer persistence shape and the improved extraction layer.
- T4 and T5 are independent of T1/T2/T3 and can be parallelised but are listed sequentially for simplicity.
- T6 (projects) before T7 (tests) so the folder layout is stable when writing server tests.
- T7 last — written against the final state of all other modules.
